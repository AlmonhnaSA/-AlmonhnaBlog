# إدارة الصور والملفات — حزمة تجهيز، ليست تفعيلًا إنتاجيًا

## الحالة والحدود
الكود جاهز للاختبار المحلي. لم تُطبّق `docs/media-storage/prepare.sql` ولم تُنشر `media-lifecycle` ولم تتغير إعدادات Vercel أو Cloud أو المشروع المستقل أو R2.

الفحص المحلي لا يرفع ولا يحذف ولا يعدّل بيانات؛ جلسة SQL للقراءة فقط وطلبات Storage هي GET. التقارير محلية بصلاحيات ملفات خاصة ولا تحتوي محتوى الجداول أو أسرارها. النتائج لا تخص الإنتاج إلا عند تشغيلها باتصال إنتاج موثّق.

**الحذف الفعلي معطّل صراحة في الخادم والسكربت.** أُضيف تنفيذ جاهز للاختبار المعزول، لا للتفعيل المباشر: إيصال مرتبط بمعاملة ناجحة وقراءة نتيجتها، فحص كامل للمراجع الحالية، فك ترميزات محافظ، وحالة `deleting` دائمة تمنع إعادة استخدام الملف. إخفاق التخزين يبقي الحماية ويُعاد بمحاولة ذات رمز جديد، ولا يُعتبر خطأ اتصال دليلًا على اختفاء الملف. سياسات Storage الحالية لم تتغير؛ بدائل تقييد الحذف والاستبدال وإعادة استخدام المفاتيح مجهّزة في ملف SQL منفصل فقط.

## تجهيز التنظيف الآمن الجديد
- `docs/media-storage/prepare.sql` ثم `cleanup.sql` ثم `storage-policies.sql`: ملفات تجهيز وليست ترحيلات مطبّقة؛ راجعها مقابل المستقل واختبرها على نسخة معزولة أولًا.
- `media_register_legacy()` يسجل **صورًا** قديمة من بيانات Storage ويعيد بناء المراجع دون تعديل المحتوى أو حذف الملفات؛ التسجيل وحده لا يمنح إذن حذف. تبقى `deletion_reviewed=false` حتى مراجعة قائمة محددة.
- الصور الجديدة المرفوعة عبر الدالة بمفاتيح فريدة تُسجل كمُدارة؛ يبقى حذفها معطّلًا بالثابت وببوابة اعتماد المشروع، وتخضع لفحص المراجع نفسه. الصور القديمة لا تُعامل كمُدارة تلقائيًا بمجرد اختفاء رابطها.
- اكتمال المصدر والنسخة الاحتياطية وسياسات التخزين والمراجع الثابتة/الخارجية مطلوب في `media_cleanup_release` بمضيف المشروع الصحيح وتاريخ انتهاء. تُسجل الحماية الفردية في `media_protections`. لا تُعدّ العلامات بديلًا عن مراجعة فعلية؛ أعد المراجعة مع كل مصدر/نشر جديد.
- الطابور يتناول مراجع أزيلت بمعاملة ناجحة فقط، وليس كل الصور غير المرتبطة. الغلاف ومعرض الخبر وصور النص والمنتجات والمتجر ومحطات الخطوط وصور الحسابات وأغلفة الصوت تخضع لحارس موحد؛ لا يمس ملفات الصوت أو PDF/المرفقات غير الصورية.
- الدالة تستخدم اتصال المشروع الذي تُنشر عليه ولا تعتمد على حسابات Lovable Cloud. موفر حذف الصور منفصل عن منطق المراجع والطابور، لإضافة R2 لاحقًا؛ **موفر R2 للصور غير منفذ الآن ولا تغيير للصوتيات**.
- بعد موافقتك فقط: تطبيق SQL المراجع على المستقل، نشر `media-lifecycle` هناك، اختبار حساب إدارة/كاتب وصورة مشتركة ومراجع داخل النص وسياسات Storage مع جلستين حقيقيتين، ثم إصدار خادم منفصل يغيّر ثابت الحذف المعطّل ونشر الواجهة بإذن. لا يكفي سر أو زر لتشغيل الحذف.
- لتكرار المحاولات بعد التفعيل، استدعاء `cleanup` بحساب إدارة يعالج إيصالات الطابور المتأخرة؛ إعداد جدولة آمنة مطلوب للتنظيف الذي فشلت محاولته دون انتظار استخدام الإدارة. لا يُنشر أو يُجدول شيء ضمن هذا العمل.
- اختبارات محلية ناجحة لا تثبت سلوك المستقل أو Cloudflare أو توفر استعادة الملفات؛ التفعيل ينتظر اختبارًا فعليًا معزولًا وموافقة منفصلة.

## تشغيل الجرد محليًا
من نسخة كود الموقع **المباشر الفعلية**، ثبّت الاعتماديات وشغّل `bun scripts/storage-inventory.ts`.
ضع القيم التالية في بيئتك المحلية فقط، لا في الواجهة ولا Git ولا المحادثة:
- `MEDIA_EXPECTED_PROJECT`: معرّف المشروع المستقل المقصود.
- `MEDIA_SUPABASE_URL`: عنوان نفس المشروع.
- `MEDIA_SERVICE_KEY`: اعتماد قراءة Storage محفوظ محليًا؛ لا يُطبع.
- `MEDIA_READONLY_DATABASE_URL`: اتصال قاعدة البيانات مع قراءة كاملة تتجاوز RLS، والجلسة نفسها تفرض القراءة فقط.
- `MEDIA_REPORT_DIR`: مجلد محلي خاص للتقارير؛ الافتراضي `/tmp/media-inventory`.
- `MEDIA_SOURCE_SCOPE_REVIEWED=true`: فقط بعد التأكد أن نسخة الكود ومجلداتها وكل الصفحات الثابتة تطابق الإنتاج.
- `MEDIA_PROTECTION_FILE`: JSON يحتوي `keys` بهوية `project/bucket/key` لملفات تستخدمها خدمات خارجية.
- `MEDIA_EXTERNAL_REVIEWED=true`: فقط بعد مراجعة الخدمات الخارجية مع المالك، لا افتراضيًا.

الاتصال المباشر يتحقق من اسم مضيف المشروع. اتصال pooler يتطلب `MEDIA_CONFIRM_POOLER_PROJECT` ويظل نطاقه غير مؤكد في التقرير حتى توفير إثبات مستقل. فقد قراءة جدول أو مصدر يمنع تصنيف الملف كمرشح عالي الثقة. لا توجد توصية حذف آمنة آليًا حتى مع اكتمال الجرد.

مخرجات: `inventory.json` و`inventory.csv`، العدد والحجم والمراجع/المراجع المحتملة وأسباب التصنيف، البايتات المحتملة للتوفير، وbase64 منفصلة عن Storage. الصور الموجودة بالكاش ليست دليلًا أن أصلها موجود؛ للتحقق من توفير مساحة فعلية يُعاد الجرد وتُراجع Storage API.

معاينة فقط: `bun scripts/storage-cleanup.ts /path/to/inventory.json`. الخيار `--execute` يرفض التنفيذ ولا يحذف ملفات.

## التفعيل لاحقًا — يحتاج موافقة منفصلة
1. تحقق من مخطط المشروع المستقل وسياساته، بما في ذلك مجلدا الترحيلات. لا تعِد تشغيل ترحيلات قديمة أو تغير buckets عميانيًا.
2. اختبر `prepare.sql` على نسخة معزولة بمستخدمين admin/writer وغير مخوّلين، واختبر صلاحيات الجداول التابعة. المعاملة Invoker تحترم RLS؛ لا تجعلها Security Definer لتجاوز سياسة مفقودة.
3. قيّم أداء الحارس العام وقفل التزامن وفك الترميزات؛ لا يُعتمد على جرد ناقص لحذف ملف. اختبر التزامن مع النسخ القديمة قبل النشر.
4. بعد إذن مستقل فقط طبّق الترحيل والدالة. لا تفعّل `MEDIA_MUTATIONS_VALIDATED=true` قبل الاختبارات. حد مرفقات المتجر يحدده المالك محليًا بالخادم `MEDIA_ATTACHMENT_MAX_BYTES`؛ لا تُفرض قيمة تجارية جديدة هنا.
5. نسخ الملفات القديمة والمراجعة والاعتماد بقائمة منفصلة قبل تفعيل إصدار الحذف المجهز. استعادة ملف محذوف تحتاج نسخة بايتات فعلية، لا مجرد تراجع في الكود.

## توافق التجربة والتراجع
في غياب الخدمة الجديدة يبقى رفع الصور إلى التخزين الحالي والحفظ القائم، **دون حذف ملفات**؛ يظهر فقط فشل حقيقي عند تعذر العملية. المسارات متعددة الجداول تتحقق من الأخطاء لكن لا تصبح ذرية قبل تفعيل RPC المجهز. المسار الجديد يستخدم مفاتيح رفع فريدة، سجلًا مؤقتًا، والتحقق ثم حفظًا ذريًا وقراءة النتيجة.

لا تغيير لروابط الصور القديمة أو جودة عرضها أو مخطط الصوت. صور المحرر الجديدة تُرفع بدل base64؛ القديمة لا تُعاد كتابتها. صور PDF تمر بمسار تحسين موحد؛ الأصل المرفق محفوظ دون تعديل. ملفات المتجر الأصلية المخصصة للتنزيل لا تُضغط.

التحقق المحلي: `bun test tests/mediaReferences.test.ts tests/mediaInventory.test.ts tests/mediaLifecycle.test.ts tests/imageUploadRules.test.ts tests/mediaCleanup.test.ts tests/mediaCleanupSql.test.ts tests/mediaStorageProvider.test.ts`. اختبار SQL محلي معزول لا يثبت إعدادات الإنتاج أو جلسات المستخدمين الحقيقية. تحقق كامل على المستقل وتجربة توفير مساحة ينتظران الوصول والموافقة المنفصلة.
