# إدارة الصور والملفات — حزمة تجهيز، ليست تفعيلًا إنتاجيًا

## الحالة والحدود
الكود جاهز للاختبار المحلي. لم تُطبّق `docs/media-storage/prepare.sql` ولم تُنشر `media-lifecycle` ولم تتغير إعدادات Vercel أو Cloud أو المشروع المستقل أو R2.

الفحص المحلي لا يرفع ولا يحذف ولا يعدّل بيانات؛ جلسة SQL للقراءة فقط وطلبات Storage هي GET. التقارير محلية بصلاحيات ملفات خاصة ولا تحتوي محتوى الجداول أو أسرارها. النتائج لا تخص الإنتاج إلا عند تشغيلها باتصال إنتاج موثّق.

**الحذف الفعلي معطّل صراحة في الخادم والسكربت.** الطابور معاينة فقط. المطابقة SQL الخام ليست كافية للروابط المشفرة؛ لا تفعّل حذفًا عبر تغيير سر أو علم في المتصفح. يحتاج إصدارًا مستقلًا بعد استكمال حراسة المراجع المشفرة وفحص التزامن والنسخة الاحتياطية والموافقة. سياسات Storage الحالية لا تزال تسمح بالحذف المباشر لبعض المالكين؛ هذه الحزمة لا تغيّرها ولا تدّعي حماية عالمية.

## تشغيل الجرد محليًا
من نسخة كود الموقع **المباشر الفعلية**، ثبّت الاعتماديات وشغّل `bun scripts/storage-inventory.ts`.
ضع القيم التالية في بيئتك المحلية فقط، لا في الواجهة ولا Git ولا المحادثة:
- `MEDIA_EXPECTED_PROJECT`: معرّف المشروع المستقل المقصود.
- `MEDIA_SUPABASE_URL`: عنوان نفس المشروع.
- `MEDIA_SERVICE_KEY`: اعتماد قراءة Storage محفوظ محليًا؛ لا يُطبع.
- `MEDIA_READONLY_DATABASE_URL`: اتصال قاعدة البيانات مع قراءة كاملة تتجاوز RLS، والجلسة نفسها تفرض القراءة فقط.
- `MEDIA_REPORT_DIR`: مجلد محلي خاص للتقارير؛ الافتراضي `/tmp/media-inventory`.
- `MEDIA_SOURCE_SCOPE_REVIEWED=true`: فقط بعد التأكد أن نسخة الكود ومجلداتها وكل الصفحات الثابتة تطابق الإنتاج.
- `MEDIA_PROTECTION_FILE`: JSON يحتوي `keys` بهوية `project/bucket/key` لملفات تستخدمها خدمات خارجية.
- `MEDIA_EXTERNAL_REVIEWED=true`: فقط بعد مراجعة الخدمات الخارجية مع المالك، لا افتراضيًا.

الاتصال المباشر يتحقق من اسم مضيف المشروع. اتصال pooler يتطلب `MEDIA_CONFIRM_POOLER_PROJECT` ويظل نطاقه غير مؤكد في التقرير حتى توفير إثبات مستقل. فقد قراءة جدول أو مصدر يمنع تصنيف الملف كمرشح عالي الثقة. لا توجد توصية حذف آمنة آليًا حتى مع اكتمال الجرد.

مخرجات: `inventory.json` و`inventory.csv`، العدد والحجم والمراجع/المراجع المحتملة وأسباب التصنيف، البايتات المحتملة للتوفير، وbase64 منفصلة عن Storage. الصور الموجودة بالكاش ليست دليلًا أن أصلها موجود؛ للتحقق من توفير مساحة فعلية يُعاد الجرد وتُراجع Storage API.

معاينة فقط: `bun scripts/storage-cleanup.ts /path/to/inventory.json`. الخيار `--execute` يرفض التنفيذ ولا يحذف ملفات.

## التفعيل لاحقًا — يحتاج موافقة منفصلة
1. تحقق من مخطط المشروع المستقل وسياساته، بما في ذلك مجلدا الترحيلات. لا تعِد تشغيل ترحيلات قديمة أو تغير buckets عميانيًا.
2. اختبر `prepare.sql` على نسخة معزولة بمستخدمين admin/writer وغير مخوّلين، واختبر صلاحيات الجداول التابعة. المعاملة Invoker تحترم RLS؛ لا تجعلها Security Definer لتجاوز سياسة مفقودة.
3. قيّم أداء الحارس العام وقفل التزامن؛ لا يُعتمد على جرد ناقص أو المطابقة الخام لحذف ملف. اختبر التزامن مع النسخ القديمة قبل النشر.
4. بعد إذن مستقل فقط طبّق الترحيل والدالة. لا تفعّل `MEDIA_MUTATIONS_VALIDATED=true` قبل الاختبارات. حد مرفقات المتجر يحدده المالك محليًا بالخادم `MEDIA_ATTACHMENT_MAX_BYTES`؛ لا تُفرض قيمة تجارية جديدة هنا.
5. نسخ الملفات القديمة والمراجعة والاعتماد بقائمة منفصلة قبل أي تطوير لإصدار الحذف. استعادة ملف محذوف تحتاج نسخة بايتات فعلية، لا مجرد تراجع في الكود.

## توافق التجربة والتراجع
في غياب الخدمة الجديدة يبقى رفع الصور إلى التخزين الحالي والحفظ القائم، **دون حذف ملفات**؛ يظهر فقط فشل حقيقي عند تعذر العملية. المسارات متعددة الجداول تتحقق من الأخطاء لكن لا تصبح ذرية قبل تفعيل RPC المجهز. المسار الجديد يستخدم مفاتيح رفع فريدة، سجلًا مؤقتًا، والتحقق ثم حفظًا ذريًا وقراءة النتيجة.

لا تغيير لروابط الصور القديمة أو جودة عرضها أو مخطط الصوت. صور المحرر الجديدة تُرفع بدل base64؛ القديمة لا تُعاد كتابتها. صور PDF تمر بمسار تحسين موحد؛ الأصل المرفق محفوظ دون تعديل. ملفات المتجر الأصلية المخصصة للتنزيل لا تُضغط.

التحقق المحلي: `bun test tests/mediaReferences.test.ts tests/mediaInventory.test.ts tests/mediaLifecycle.test.ts tests/imageUploadRules.test.ts`. اختبار SQL محلي معزول لا يثبت إعدادات الإنتاج أو جلسات المستخدمين الحقيقية. تحقق كامل على المستقل وتجربة توفير مساحة ينتظران الوصول والموافقة المنفصلة.
